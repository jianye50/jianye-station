我用中文写。我读到的关于我写的东西的大部分都是英文的。多年来，这种不匹配的感觉一直在我的脑海里，从未出现在页面上——我会发表一篇文章，国外的朋友会打开它，看到一堵字符墙，然后礼貌地关闭标签。

显而易见的解决方法是将所有内容都写两次。我尝试了大约三篇文章。它无法与现实接触：第二个版本始终是第一个版本的摘要，而不是第一个版本的翻译，几周后你完全停止发布第二个版本。

因此修复移至页面本身。现在，这里的每篇文章都带有其所用的语言，并且该网站会根据需要翻译成访问者正在阅读的任何内容。这篇文章是特意用英语写的——如果你现在正在阅读中文，那么下面的机制就是将它放在你面前的。

## 天真的版本，以及为什么失败

第一次尝试是一个按钮。点击它，整个页面变成另一种语言，完成。三件事立即破裂：

- **按钮是读者必须做出的决定。**大多数人都不会这样做。他们反而离开了。
- **整页翻译没有粒度。** 一句话改变，你再次通过引擎发送整篇文章。
- **没有人记得他们的选择。** 在手机上重新加载页面，您就会回到原来的语言。

幸存下来的版本颠倒了这三个版本。正常情况下没有按钮 - 页面会检测它使用的语言，检测访问者想要的语言，并且仅在两者不同时才进行操作。工作单元是文本块，而不是文档。结果按内容缓存，因此访问者只需支付一次翻译费用，无论他们回来多少次。

## 谁决定这是什么语言

两个问题，而且它们不是同一个问题：

1. **访客**想要什么语言？
2. **这篇文章**实际上是用什么语言写的？

第一个问题有一个简单的答案：浏览器的 `navigator.language`，通过网站自己的语言切换所说的内容进行完善。中文语言环境得到中文；其他一切都变成英语。

第二个是有趣的地方，因为文件名是谎言。名为 `one-post-two-languages` 的文件夹中的一篇文章可能仍然是用中文编写的。名为 `index.zh.md` 的文件可能是有人忘记重命名的英文草稿。

因此，检查针对的是内容，而不是名称：根据拉丁字母计算 CJK 字符，忽略标签和代码，让多数人决定。如果一篇文章主要是CJK，那么它就是中文文章。如果大部分是拉丁字母，几乎没有中日韩字母，那么它就是英文字母。没有第三种情况值得处理——混合脚本散文非常罕见，错误的猜测会花费一个段落，而不是一篇文章。

> [!注意]
> 方向比听起来更重要。 “翻译成英文”和“翻译成中文”是两个完全独立的工作，具有独立的模型、独立的缓存和独立的故障模式。将它们视为带有参数的一项工作可以使代码具有可读性；将它们视为一个缓存是错误的原因。

## 三个引擎，一个队列

没有哪一种翻译服务足够可靠，可以成为唯一的翻译服务。该网站按顺序使用了三个：

|发动机|它在哪里运行 |为什么是第一 |
| ---| ---| ---|
| Chrome 内置翻译器 |在访问者的浏览器中 |免费、私密、无网络跳跃 |
|网站代理|服务器端功能|适用于所有浏览器 |
|谷歌翻译端点 |直接从页面 |代理被限制时的最后手段 |

第一个值得一个段落。 Chrome 现在提供了一个在本地运行的翻译模型 - 文本永远不会离开设备，并且没有配额可以耗尽。当它可用时，它无疑是最佳选择：零成本、首次加载后零延迟、零隐私问题。

它也是针对每种语言对的，并且需要下载模型才能翻译任何内容。所以该页面并不假设它存在。它会询问 API 是否存在，是否支持特定对，以及模型是否已准备好 - 如果其中任何一个答案为“否”，则请求将被传递到下一个引擎，除了稍长的等待时间之外，读者不会注意到任何事情。

> [!警告]
> 服务器端代理不是您可以忽略的备胎。公共翻译端点按 IP 进行速率限制，而共享云 IP 在糟糕的一天将达到该限制。当发生这种情况时，失败看起来像是“翻译默默地停止工作”而不是错误，因为页面不断尝试，队列不断等待。保持客户端路径处于活动状态。

## 缓存是一个特性

上面的一切都是管道。缓存是实际产品决定的。

翻译一个页面的速度足够慢，以至于可以看到——如果连接良好，需要一两秒，如果连接不好，则要慢得多。每次访问时再次执行此操作会将一个聪明的功能变成一种税。因此，每个翻译的块都存储在本地，由三件事决定：

- 它所属的文章
- 源文本的哈希值
- 翻译方向

哈希使得编辑变得便宜。更改一个段落，只有该段落的哈希值发生变化 - 其他四十个块仍然有效并且永远不会离开缓存。重写标题，标题是唯一重新发送的内容。

方向后缀是容易出错的部分。如果没有它，将一篇文章翻译成英文然后再翻译回中文会覆盖同一个插槽，并且双语读者在版本之间切换会不断驱逐自己的缓存。两个方向，两个命名空间，互不干扰。

> [!提示]
> 添加反向方向时，保持旧的缓存键正常工作。在更改之前阅读网站的访问者仍然拥有原始密钥下的条目；在原始方向上重用该密钥意味着它们的缓存在升级后仍然存在，并且只有新方向开始为空。

## 何时人工翻译应该获胜

机器输出对于段落来说已经足够好了。对于必须落地的标题、必须与网站词汇相匹配的标签列表或必须说服某人点击的摘要来说，这还不够好。

因此该网站首先检查手写版本。如果文章文件夹包含另一种语言的同级文件，则该文件获胜，并且引擎永远不会运行。后备链故意短而无聊：

1. 人工翻译（如果存在）
2. 本地模型，如果已准备好
3.服务器代理
4. 公共端点
5. 原文，悄悄提示无法翻译

第五步很重要。一个大声失败的页面比一个假装的页面更好：如果所有四个引擎都宕机了，显示原文并说出来，而不是显示一篇空文章并让读者假设该网站已损坏。

## 这不能做什么

诚实地面对这些限制比在公共场合发现它们要便宜。

- **布局无法翻译。** 英文中一行可以容纳的句子在中文中需要两行。标题变得很长，表格变得很拥挤，而且没有引擎会为你重排段落——这就是 CSS 的工作，但它只成功了一半。
- **代码是一个雷区。** 标识符、文件路径和内联片段必须保持不变。任何通过翻译器来回传输文本的内容都需要一种方法来保护它们，而这种保护总是会略有漏洞。
- **语气变平。** 我的中文写作有一个我刻意选择的节奏。英文版有意思，没有节奏。对于可接受的技术职位；对于任何我关心的散文，这是我自己写第二个版本的原因。
- **第一个访问者付费。** 每一篇新文章，以另一种语言，都会由先到达的人翻译一次，然后为后面的每个人缓存。在一个每天有十个读者的网站上，这很好。在一个有一万个站点上，你会预先计算。

## 简短版本

分别检测读者的语言和文章的语言，仅在它们不同时进行翻译，逐块进行，以便编辑成本低廉，按内容哈希和方向进行缓存，并让手写翻译覆盖机器（无论何时存在）。

这些都不是什么新鲜事。它值得建立的地方在于它消除了借口：这个博客没有英文版本的原因从来都不是技术。出版两次是一件苦差事，而人们不做苦差事。一个可以自我翻译的页面不需要被说服。
