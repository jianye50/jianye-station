有一个文件。它是 `index.html`，长度为 357,918 个字符，并且是整个站点。没有捆绑器，没有 `node_modules`，除了上传之外没有部署管道。当我想发布时，我编辑文件并推送。

人们认为这是我正在解决的一个限制。老实说，一开始我很懒——我想在周日下午写一个博客，但不想花时间选择静态站点生成器。让我惊讶的是，约束一直在支付租金。十五个月后我会再次选择它，但我会遇到两个例外。

## 约束完成设计工作

框架为您提供选择。选择不是免费的：每一个选择都是你必须做出的决定，而大多数选择你会在凌晨 1 点做出糟糕的决定。

通过一个文件，一半的决定已经为我做出了：

- **没有依赖项升级**，因为没有依赖项。该网站十五个月内没有因为与我自己的代码无关的原因而崩溃过。
- **没有构建步骤**，因此我编写的内容和运行的内容之间没有差距。当出现问题时，产生该问题的文件就是我可以读取的文件。
- **没有路由库**，因此导航是我完全理解的六十行 `hashchange` 处理 - 包括浏览器在错误位置恢复滚动的部分。
- **没有 CSS 架构争论。** 在同一个文件的顶部有一个样式表，它有 4,000 行，因为我从来不需要证明其中任何一个的合理性。

最后一个是双向的。下面详细介绍一下。

## 实际成本是多少

我不会假装该文件在速度较慢的笔记本电脑上打开起来很舒服。三件事真正伤害了我们：

1. **搜索是唯一的导航。** `Ctrl+F`立即找到`function renderPost`；它并不能帮助我记住我想要的东西是在一个名为 `wireMedia` 的 900 行块中的 `setTimeout` 内。
2. **合并冲突是完全存在的。** 对同一文件的两次编辑永远不会合并。由于我是唯一的作家，这是理论上的，但这就是我永远不会向团队推荐这种形状的原因。
3. **每次加载都会解析所有内容。** 浏览器读取 350 KB 的标记和脚本来显示 2,000 个字符的帖子。

第三个听起来比实际情况更糟糕。 Gzip 压缩后的大小约为 55 KB，解析一次。停留三十秒的读者和停留十分钟的读者支付相同的费用。与典型的营销页面渲染标题所需的 300 KB JavaScript 相比，这并不是看起来那么荒谬的选择。

> 对架构的真正考验不是它如何处理第一个功能。当你忘记了为什么第一个是这样建造的时，这就是它处理第四十个的方式。

## 我会停下来的地方

两个地方，都是关于我无法在脑海中记住的状态。

第一个是有多个作家的任何事情。当第二个人需要接触这个文件时，整个争论就崩溃了——不是因为代码变得更糟，而是因为协调成本从“从不”变成了“不断”。

第二个是必须恢复的任何事情。住在 `/admin` 的编辑已经突破了极限：草稿恢复、上传队列、每个帖子的历史记录。该代码是文件中最不令人愉快的部分，这并非偶然。单个文件非常擅长渲染，但非常不擅长保持时间线。

## 我没想到的部分

这种限制改变了我所写的内容。当发布需要一次编辑时，我会发布更多内容，并且发布较小的内容 - 一条注释，一张屏幕截图，一段无法在较重的网站上发布“真实”帖子的仪式中幸存下来的段落。

这比 55 KB 更有价值。
